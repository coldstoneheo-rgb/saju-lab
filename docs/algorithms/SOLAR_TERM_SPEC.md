# Solar Term & Pillar Calculation Spec (Draft)

## 목적
- 절기(24절기) 기준 월주 계산의 경계 조건을 명확히 정의
- 양력 입력에서 연/월/일/시주 산출을 위한 입력/출력 요구사항을 정리

## 입력 요구사항
- 양력 생년월일 (YYYY-MM-DD)
- 출생시간 선택 (HH:mm)
- 타임존 (기본 Asia/Seoul)

## 절기 기반 월주 규칙(개요)
- 월주는 **절기 기준**으로 구분
- 경계: 특정 절기의 정확한 시각 이전/이후로 월주가 달라짐
- 예: 입춘 이전 → 전년도 절기 체계, 입춘 이후 → 새 연도 기준

## 계산 단계(개요)
1. 입력을 타임존 기준으로 표준화
2. 해당 날짜/시간에 대응하는 **절기 경계** 계산
3. 절기 경계를 기준으로 월주 산정
4. 천간/지지 60갑자 순환으로 연/월/일/시주 산출

## 경계 조건 체크리스트
- 절기 경계 시각과 동일한 시각 입력 시 처리 규칙 명확화
- 출생시간 미상 시 월주/시주 처리 규칙
- 윤년, 윤달(음력 변환이 필요 시) 처리 여부 명확화

## 경계 시각 처리 규칙(결정)
- 절기 경계 시각과 **동일한 시각** 입력은 **새 절기 적용**으로 처리
- 절기 경계 **이전**은 이전 절기 기준 월주 유지
- 절기 경계 **이후**는 다음 절기 기준 월주 적용

## 입춘 기준 연주 변경 규칙(결정)
- 연주는 **입춘 시각을 기준**으로 변경
- 입춘 이전 출생: 전년도 연주 적용
- 입춘 이후(동시각 포함) 출생: 해당 연도 연주 적용

## 예시 케이스

### 예시 1: 입춘 직전
- 입력: 2024-02-04 07:59 Asia/Seoul
- 규칙 적용: 입춘 이전 → 전년도 연주 적용

### 예시 2: 입춘 동시각
- 입력: 2024-02-04 08:00 Asia/Seoul
- 규칙 적용: 입춘 동시각 → 해당 연도 연주 적용

### 예시 3: 절기 경계 동시각
- 입력: 절기 경계 시각과 동일
- 규칙 적용: 새 절기 기준 월주 적용

### 예시 4: 하지 직전/직후
- 입력: 2010-06-21 23:59 Asia/Seoul (하지 직전)
- 규칙 적용: 하지 이전 → 이전 절기 기준 월주

### 예시 5: 동지 직전/직후
- 입력: 2015-12-22 00:30 Asia/Seoul (동지 직후)
- 규칙 적용: 동지 이후 → 다음 절기 기준 월주

### 예시 6: 월주 변경 케이스(절기 경계 전후)
- 입력: 절기 경계 전 1분
- 규칙 적용: 이전 절기 기준 월주 유지

### 예시 7: 월주 변경 케이스(절기 경계 동시각)
- 입력: 절기 경계 시각 정확히 일치
- 규칙 적용: 새 절기 기준 월주 적용

## 검증 전략
- KASI 등 공공 절기 데이터와 비교
- 공개 절기표와 결과 대조
- 골든 픽스처로 일관성 검증
- 입춘과 월주 변경 절기는 경계 전 1분, 경계 동시각, 경계 후 1분을 테스트한다.
- 내장 절기표는 2026-09-22부터 **한국천문연구원 24기 입기 시각 표(1920-2100)의 생성물**이다. 아래 «지원 범위» 참조.
- 독립 천문 계산(astronomia VSOP87)으로 표를 3자 검증한다: `node scripts/verify_solar_terms_astronomia.mjs`.

## 산출물
- `calculatePillars(input)`에서 절기 계산 모듈 분리
- 경계 시각 데이터는 캐시 가능

## Phase 2A 구현 범위
- 현재 계산 코어는 `Asia/Seoul`만 지원한다.
- 절기 경계 데이터는 fixture와 경계 테스트에 필요한 연도부터 내장한다.
- 입춘 동시각은 새 연주/월주 적용으로 처리한다.
- 출생시간이 없고 입력일이 입춘 또는 월주 변경 절기 경계일이면, 정오 등 임의 시각으로 추정하지 않고 시간 입력이 필요하다는 에러를 낸다.
- 월주는 12개 월 경계 절기(입춘, 경칩, 청명, 입하, 망종, 소서, 입추, 백로, 한로, 입동, 대설, 소한)를 기준으로 한다.
- 23:00 이후 자시를 다음 날짜 일주로 넘기는 옵션은 아직 구현하지 않는다.
- 지원 범위 밖 날짜는 잘못된 값을 조용히 반환하지 않고 에러를 낸다.

## Phase 2D 경계 테스트 보강
- 2024-02-04 입춘 경계는 17:26, 17:27, 17:28을 테스트한다.
- 2024-03-05 경칩 월 경계는 KASI 기준 11:22, 11:23, 11:24를 테스트한다.
- 경계 동시각과 경계 이후 1분은 새 절기 기준으로 처리한다.
- 경계 이전 1분은 이전 절기 기준을 유지한다.
- 현재 MVP는 23:00 이후 자시를 다음 civil date의 일주로 넘기지 않는다. 예: 2010-06-21 23:00은 2010-06-21의 일주를 유지하고 시지만 자시로 계산한다.
- 23:00 이후 일주 rollover를 지원하려면 별도 제품 결정, 사용자 안내, fixture 재검증, 호환성 테스트가 필요하다.

## Phase 2E fixture matrix 확장
- 2024년 월주 변경 절기 중 청명, 입하, 망종, 소서, 입추, 백로, 한로, 입동, 대설의 경계 전 1분, 경계 동시각, 경계 후 1분을 테스트한다.
- 2024년 경계일에 출생시간이 없으면 월주를 정오 등으로 추정하지 않고 `birthTime is required` 에러를 유지한다.
- 2024-12-07 대설 이후의 월 경계 상한 검사를 위해 2025-01-05 소한과 2025-02-03 입춘 경계만 내장한다.
- 이 단계는 넓은 연도 범위의 절기 데이터 ingestion이 아니라, 검증 가능한 2024년 fixture matrix를 추가하는 제한 범위다.
- 공개 베타 전에는 내장 절입 시각을 KASI 원자료와 다시 교차 검증한다.
- Phase 4S는 `docs/SOLAR_TERM_SOURCE_AUDIT_2026-05-25.md`에 내장 경계값, 현재 출처 상태, KASI 재검증 체크리스트를 기록한다. 이 문서는 재검증 준비 자료이며, 재검증 완료 증거가 아니다.
- Phase 4T는 `docs/KASI_SOLAR_TERM_REVALIDATION_2026-05-25.md`에 KASI 2024/2025 역서 대조 증거를 기록했다. Phase 4U는 1분 차이 행을 KASI 기준으로 맞췄으며, 이 검증 범위는 내장 2024 matrix와 2025 상한 경계에 한정된다.

## 지원 범위 (2026-09-22 갱신)

- 내장 월 경계 절기표는 한국천문연구원이 공개한 **24기 입기 시각 표(1920~2100년, KST=UTC+9 고정)**
  `docs/fixtures/kasi-24-solar-terms-1920-2100_20260902.txt`에서 **생성**한다.
  출처: `https://astro.kasi.re.kr/kor/almanac/solarTerms/download`, 다운로드 2026-09-22,
  sha256 `508761248c7d18eb…`. 손으로 편집하지 않는다: `scripts/generate_solar_terms_module.py` →
  `packages/saju-core/src/solar-terms.data.ts`. CI가 `--check`로 생성물이 최신인지 확인한다.
- 표는 24기 4,344행이지만 월주에는 12절만 쓰므로 **2,172행(12 × 181년) + 입춘 181행**을 내장한다.
- 계산 가능 구간: **1920-01-06 23:41 소한 ~ 2100-12-07 10:42 대설 직전**.
  1919년 이전은 입춘 행이 없어 `No Ipchun boundary`, 2100-12-07 대설 이후는 다음 경계가 없어
  `No upper solar month boundary`로 거부한다(API 계약에서는 둘 다 `OUT_OF_SUPPORTED_RANGE`).
- KASI 표는 반올림이 날짜를 넘기는 경우 «24시 0분»으로 적는다(1950 대한·2030 우수·2053 대한 3건).
  생성기는 이를 익일 00:00으로 접지만 세 건 모두 중기라 내장 행에는 나타나지 않는다.
- 표는 UTC+9 고정이며 과거 표준자오선과 서머타임을 반영하지 않는다. 그래서 계산 코어는 입력 벽시계를
  비교 전에 **KST 벽시계로 환산**한다 — 아래 «한국 시간대 이력 정규화».
- 미래(2030년대 이후) 값은 KASI 스스로 «수 초~수 분 달라질 수 있음»이라 밝힌다. 3자 검증에서도
  2052년부터 ΔT 예측 모델 차이로 60초를 넘는 행이 나타나며(최대 172초, 2090년대), 이는 데이터 결함이
  아니라 예측 불확실성이다. 새 표가 공개되면 txt를 교체하고 생성기를 다시 돌린다.
- 이전 소스였던 data.go.kr 특일 정보 API 픽스처(`kasi-special-days-solar-terms-2000-2028.json`)는
  대조 증거로 보관한다. 두 KASI 산출물의 차이(1분 19행, 2011-11-08 입동 5시간 51분 1행)와 판정은
  `docs/SOLAR_TERM_SOURCE_AUDIT_2026-05-25.md` «2026-09-22 판정»에 있다. txt 배포에 문제가 생기면
  `--source docs/fixtures/kasi-special-days-solar-terms-2000-2028.json`으로 2000-2028 표를 되살릴 수 있다.

## 한국 시간대 이력 정규화 (2026-09-22)

- 출생 기록의 시각은 그날 한국 시계가 가리킨 값이고, 절기표는 UTC+9 고정이다. 둘을 맞추기 위해
  `packages/saju-core/src/timezone-history.data.ts`(IANA tzdb 2026d `asia`의 Zone Asia/Seoul + Rule ROK,
  행마다 원문 인용)와 `normalizeToKstWallClock()`이 입력을 `kst = local − (offsetAt(local) − 540분)`으로 환산한다.
  이후 절입 비교·일주(epoch day)·시주는 전부 환산값을 쓴다. 일주 경계는 **KST 자정**이다.
- 표준시: 1908-04-01 +08:30 → 1912-01-01 +09:00 → 1954-03-21 +08:30 → 1961-08-10 +09:00. 1945-09-08의 JST→KST는
  오프셋 변화가 없어 행이 없다. 1908-04-01 이전(LMT 8:27:52)은 지원하지 않는다(절기표 시작 1920보다 앞).
- 서머타임(+1h): 1948·49·50·51(개시 0:00, 종료 24:00), 1955~60(같은 규칙, +08:30 위라 UTC+9:30), 1987·88(개시 2:00, 종료 3:00).
- 응답 `resolution: { appliedOffsetMin, flags }`. `appliedOffsetMin`은 환산에 뺀 분(−30 = 30분 더함, +60 = 1시간 뺌).
  `flags`: `utc+8:30`(표준시가 +08:30인 날), `dst`, `ambiguous`(종료일 되감기로 두 번 있던 시각 — 첫 번째(서머타임) 채택),
  `nonexistent`(개시일 건너뛴 시각 — 전이 전 오프셋 유지). 2000년 이후는 항상 `0`·빈 배열이다.
- 시각 미상 출생은 정오 기준으로 오프셋만 보고하고 날짜는 그대로 둔다. 오프셋이 0이 아닌 날엔 경계일 판정을
  전날·다음날까지 넓혀서(`boundaryDateSlackDays = 1`) 시각 없는 입력을 거부한다.
- 전이 시각 28개는 이 머신 Node 22/ICU 77(tz 2025b)의 `Intl.DateTimeFormat("Asia/Seoul")`과 ±1분에서 일치한다
  (`timezone-history.test.ts`). 진태양시·분 단위 시주·23시 정책은 다음 단계다.

### 왜 런타임 호출이 아닌가
계산 코어는 결정론이어야 하고 오프라인에서 같은 값을 내야 한다. 외부 API를 요청 시점에 부르면
가용성·지연·키 관리가 계산 결과의 전제가 된다. 그래서 API는 **생성 시점 소스**로만 쓰고,
저장소에는 생성된 표와 그 근거 픽스처를 함께 커밋한다.
